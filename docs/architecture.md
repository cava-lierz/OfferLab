# 系统架构与接口约定

我把一次面试的进度保存在本机，由后端决定当前题目、追问上限和结束条件。学校面试官按请求完成备课、追问决策或复盘。这样即使模型调用中断，已经提交的回答和面试进度也能从 SQLite 恢复。

```text
浏览器里的 React 页面
    │ /api，经 Vite :5173 代理
    ▼
FastAPI :8000 ⇄ SQLite（面试记录、任务、分题复盘）
    │ 后台线程领取任务
    ├─ 演示模式 → 本地题库和规则
    └─ OpenClaw 模式 → 本机隧道 :18790 → 学校 Gateway :18789 → Agent 与模型
```

开发服务和 `vite preview` 都会代理 `/api`。如果单独托管 `frontend/dist/`，还需要运行 FastAPI，并将同源的 `/api` 请求转给它。目前的运行方式面向本机单用户。

## 面试计划与模型调用

准备页把简历文本、目标岗位、可选的 JD 和题数交给后端。后端创建记录，把 `plan` 任务排队，并用 HTTP 201 把持久化 ID 返回给页面。模型返回恰好 `main_count` 道主问题，每题包含主题 `topic` 和题干 `question`。后端保存整份计划，前端显示主问题数量和开始按钮，点「开始面试」才展示第一题。

学校专用面试官还会给出每题的考查依据 `criterion`。例如，围绕表单改版，它可以考查候选人怎样把访谈发现转成设计选择。备课时 Agent 可用公开的岗位、公司、职级或轮次关键词调用 `web_search`，摘要不足时再用 `web_fetch` 读原文。检索词限于公开岗位信息，简历和回答作为本场模型输入。采用的来源以标题和 URL 存入 `research`，最多四条。后端检查状态与来源是否匹配，并校验链接格式。准备页、报告和导出可展示这些来源。学校端的运行轨迹记录实际工具调用。[学校 Agent 部署](../openclaw/DEPLOYMENT.md)

请求学校模型时，后端使用 Bearer 认证向 `/v1/chat/completions` 发送 `model: openclaw`、`stream: false`，HTTP 客户端用 `trust_env=False` 直连隧道。指定 `OPENCLAW_AGENT_ID=interviewer` 后，请求头 `x-openclaw-agent-id` 把任务交给专用工作区。专用 Agent 用 `read` 读取 Skill、题库和评分标准。默认 Agent 则由后端把本地规则及参考材料放入系统提示。每次请求都带上本阶段所需的资料快照，并以 `offerlab-{interview_id}-{request_uuid}` 标识独立调用。这样可以从本机记录还原上下文，代价是后续请求要重复传入部分材料。

## 回答提交与面试状态

浏览器给回答带上两个标识。`question_id` 说明答的是哪一道题，`request_id` 标识这次提交。FastAPI 调用 `Engine.submit`，在同一次 SQLite 写入中保存回答和等待处理的任务，然后返回 202。因此，客户端收到 202 时回答已持久化，模型决策可以稍后完成。如果提交时网络断了，同一请求用相同的题目和文字重发，只会取回已有记录。重复使用标识却改了内容，或从另一个标签页提交过期题目，都会收到 409。

后台线程随后调用 `Engine.process_job`。在 `decision` 阶段，模型只需返回 `followup` 和一个追问，或返回 `next` 结束本题。若已追问两次，后端直接结束这道主问题。

| 面试记录的状态 | 触发条件与结果 |
| --- | --- |
| `preparing` → `ready` | 计划通过校验，等候选人点「开始面试」。 |
| `active` → `awaiting_next` | 当前题的回答已保存，后台判断是否追问。 |
| `awaiting_next` → `active` | 仍需补充信息，页面展示同一道主问题的追问。 |
| `awaiting_next` → `between_questions` | 本题已结束，还有主问题。点「下一题」后回到 `active`。 |
| `awaiting_next` → `reporting` | 最后一组问答结束，可以点按钮生成复盘。已有回答时也可在任务空闲时提前结束，直接提交报告任务。 |
| `reporting` → `completed` | 报告通过校验，可以回看、导出和重新练习。 |

## 切题与分题复盘

下一道主问题已经在计划里，所以 `POST /next` 可以直接返回 200。切题时，后端用一次事务保存新题，并将上一道主问题及其追问的回答交给分题复盘队列。请求带上刚结束的题目 ID，重复点击同一次切题不会跳过下一道题。

这份分析单独存在 `question_reviews` 表中，每个 `(interview_id, main_index)` 只有一条。专门的线程在没有排队的前台任务时领取它，记下本次尝试、执行者和截止时间。它只更新自己的记录，因此候选人可以继续答题。已经开始的调用会继续运行，过期尝试的结果无法写回。

总报告生成时，模型拿到全部回答和已经完成的分题分析。正在分析或失败的题目可以直接按回答原文复盘，尚未开始的分题任务会跳过。最后一题也由总报告直接处理。这样可以把部分工作放到候选人作答期间，每场最多增加 `main_count - 1` 次模型调用。实际能节省多少等待时间取决于学校模型的并发能力和作答时长。[验证记录](verification.md)

## 评分依据与引文校验

`report` 要按表达结构、项目深度、岗位匹配、反思能力的顺序返回四项反馈和练习建议。每个分数必须是 0–100 的整数，且至少有一条引文。若证据不足，允许 `score=null`。演示模式总是保留空分数。

我用回答 ID 和连续原文来约束评分依据。例如，候选人的回答是“我访谈了 12 位同学”，报告可以引用“访谈了 12 位同学”，但如果把人数写成 20，这条引文就无法通过校验。后端按 `answer_id` 定位回答，再检查 `quote` 是否完整出现在原文中。任一引文不符，后端会拒绝整份报告并保留重试入口。这项校验确认引文出处，评价本身的合理性仍需结合题目和上下文判断。分题分析使用同一套校验。

## 任务持久化与中断恢复

面试主体是一条 JSON 快照。一次保存会更新问答、当前阶段和版本号 `revision`。前端用版本号合并提交结果与轮询结果，让迟到的旧响应无法覆盖新回答。答题草稿另存于浏览器的 `offerlab:answer:{interview_id}:{question_id}`，附带稳定的请求 ID。修改回答后生成新 ID，服务端确认保存后清除草稿。浏览器拒绝本地存储时，页面仍能输入，并提示草稿保存受限。

`generation` 单独描述当前任务。它包含 `id`、`task`、`status`、`phase`、`timeout_seconds`，以及排队、开始、截止、结束的时间。任务从 `queued` 到 `running`，最后进入 `completed` 或 `failed`。收到模型结果后才进入 `validating`。生成失败会保留原场次和错误。对已排队或运行的任务点 `retry`，会返回同一任务。旧记录缺少 `generation`、考查依据或检索字段时也能按原有阶段继续，启动时会自动补建分题表。

每个 FastAPI 进程启动两个处理计划、追问和总报告的线程，一个分题线程，以及一个心跳线程。队列保存在 SQLite 中。前台线程领取任务后独占该场次的写入权，租约为 `max(180, timeout + 30)` 秒，期间仍可查询。连接阶段最多 5 秒，请求总时限涵盖读取响应，计划和追问默认 120 秒，复盘默认 300 秒。心跳每 2 秒更新，执行者失联超过 15 秒，或运行超出截止时间 30 秒，恢复程序会标记中断并撤销写入权。正常停机会主动注销执行者。下次启动后，排队任务可继续，已中断的前台任务由用户重试，迟到的旧结果无法覆盖新尝试。

生成期间页面每 1.5 秒串行查询一次，空闲面试和历史列表约每 5 秒查询一次。隐藏标签页的间隔至少为 10 秒，回到页面会立即刷新。查询失败时前端延长间隔并显示连接提示，离开页面会取消查询。等待生成时只用带无障碍标签的加载图标，减少动态效果设置会放慢旋转。分题分析在后台进行，答题页继续显示当前问题。

## HTTP 接口

下表中 `{id}` 是创建面试时返回的 ID。列表只返回最近 100 场的概要，进入某一场再读取简历和回答。

| 方法 | 路径 | 输入或结果 |
| --- | --- | --- |
| GET | `/api/health` | 查看本机模式、Agent 目标及 Token 是否配置。实际模型连接用 `gateway-check` 验证。 |
| POST | `/api/resumes/parse` | 上传 multipart 字段 `file`，取得可在准备页核对的文本。 |
| GET | `/api/interviews` | 读取历史概要。 |
| POST | `/api/interviews` | 提交 `{role, resume, jd?, main_count?, practice_focus?, request_id?}`。首次创建时将场次与计划任务一起保存并返回 201。同一标识和相同材料重发会返回已有场次的当前状态。材料冲突返回 409，原场次已删除返回 410。 |
| GET | `/api/interviews/{id}` | 读取完整面试快照。 |
| POST | `/api/interviews/{id}/start` | 从备好的计划取出第一题。 |
| POST | `/api/interviews/{id}/answers` | 提交 `{request_id, question_id, text}`，保存回答并排队处理。 |
| POST | `/api/interviews/{id}/next` | 提交 `{question_id}`，切题并登记上一题的复盘。 |
| POST | `/api/interviews/{id}/finish` | 提前结束已有回答的面试并提交报告任务。 |
| POST | `/api/interviews/{id}/retry` | 推进当前待处理的计划、追问决策或报告。 |
| GET | `/api/interviews/{id}/export` | 下载包含四维反馈、来源及完整问答的 Markdown。 |
| DELETE | `/api/interviews/{id}` | 在一次事务中删除本机场次与分题复盘。重复删除均返回 204，此后查询返回 404。 |

提交后仍有生成任务时通常返回 202，立即完成的操作返回 200。无效操作通常返回 400，状态冲突返回 409，记录缺失返回 404，请求字段校验失败返回 422。模型在后台失败时，下次 GET 可读到 `error` 和 `generation.status=failed`，页面据此提供重试入口。核心测试可用同步适配器 `Engine.act` 推进流程，HTTP 路由使用上面的异步任务路径。[开发与检查](development.md)

项目适配学校的 OpenClaw `2026.5.22`。框架及协议的背景资料见 [OpenClaw HTTP 接口](https://docs.openclaw.ai/gateway/openai-http-api)、[FastAPI 文档](https://fastapi.tiangolo.com/tutorial/) 和 [Vite 文档](https://vite.dev/guide/)。
