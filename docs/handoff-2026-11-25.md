# 2026 年 11 月 25 日 · 选题与初次接入记录

11 月 25 日（北京时间）交接时，我们已确定选题和初步架构，并验证了学校端的 HTTP 模型调用。前后端应用当时仍处于设计阶段。本记录保留当日的环境、方案和待办事项。后续进展分别记录在[项目首页](../README.md)和[验证记录](verification.md)。

## 课程背景与项目目标

上海交通大学 1 学分公选课《大模型与智能体工程实践》允许 2–4 人组队，答辩和报告各占 50 分，线上答辩定在 11 月 29 日上午。题目可以做行业应用案例、基于智能体的应用开发，或自主搭建与开发智能体模型。考核图列出了这几类方向，工具数量、报告格式和答辩时长当时没有明确说明。[课程要求原图](../requirement.png)

我们两人选择了应用开发方向，计划为秋招模拟面试官实现独立前端。我们的演示从候选人提交简历和目标岗位开始。面试官按材料提问，依据回答决定是否追问，最后在复盘报告中引用原话并给出练习建议。

首版计划采用文字问答，暂定每场约 5 道主问题，每道最多追问两次。岗位方向留给用户填写，Java 后端只是讨论时的例子。语音、视频、在线执行代码和多个 Agent 协作都超出了当时两个人给首版划定的范围。

## 学校容器与模型接口

我通过本机已有的 `ssh openclaw` 别名登录学校容器，记录了以下环境信息。

| 环境项 | 学校端实测值 |
| --- | --- |
| 系统与用户 | Ubuntu 22.04.5，aarch64 容器，用户 `idekube` |
| OpenClaw | `2026.5.22 (a374c3a)` |
| 默认 Agent 和模型 | `main`，`sjtu/deepseek-reasoner` |
| Gateway | `127.0.0.1:18789`，认证模式为 `token` |
| 配置与服务管理 | `~/.openclaw/openclaw.json`，Gateway 父进程为 `supervisord` |

起初模型接口返回纯文本 404。启用 `gateway.http.endpoints.chatCompletions.enabled = true` 并用 `openclaw config validate` 确认配置后，我在学校终端发起了请求。`/v1/chat/completions` 收到 `model: "openclaw"`、独立测试用的 `user` 和 `stream: false`，Token 在远端就地读入 Bearer 认证头。诊断脚本留下了这份脱敏结果。

```text
CONFIG_READ: OK
HTTP_ENABLED: True
AUTH_MODE: token
VERSION: OpenClaw 2026.5.22 (a374c3a)
HTTP_STATUS: 200
HTTP_RESPONSE: JSON
COMPLETION_PRESENT: True
ERROR_PRESENT: False
```

模型接口返回了有效回复，先前的 404 已排除。学校容器由 supervisord 管理，`systemctl --user` 在该环境不可用。日志虽出现过飞书插件警告，这次 HTTP 调用仍然成功。搜索、网页读取、安装 Skill 的权限、任务 JSON 的稳定性和流式工具事件当时都还没有实测。

## SSH 转发与本机健康探测

学校 Gateway 监听学校自己的回环地址。我在本机建立了 18790 到学校 18789 的端口转发。当时使用的 SSH 命令如下，后来的项目将它封装为 `manage.py tunnel`。[本机运行与排查](operations.md)

```bash
ssh -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 \
  -L 127.0.0.1:18790:127.0.0.1:18789 \
  openclaw
```

隧道在线时，我在另一个本机终端请求健康接口。

```bash
curl --noproxy '*' --connect-timeout 5 --max-time 10 \
  -sS -i http://127.0.0.1:18790/healthz
```

接口返回 `HTTP/1.1 200 OK` 和 `{"ok":true,"status":"live"}`。这次请求确认了本机经隧道访问学校服务的路径。交接时待验证的是从本机携带 Token 调用 `http://127.0.0.1:18790/v1/chat/completions`，以及后续网站的端到端流程。转发依赖终端中持续运行的 SSH 进程。

当时自动化执行环境无法解析学校 SSH 代理域名，访问本机转发端口也返回过 `Operation not permitted`。我在本机终端执行诊断脚本，以脱敏输出记录结果。我们计划将 Gateway Token 保存在后端私有 `.env` 中，模型 API Key 由学校管理，前端仅访问本机 API。仓库提供占位示例，并通过 `.gitignore` 排除私有配置、简历、数据库、日志和依赖目录。

## 首版设计草案

**准备。** 前端拟用 React、TypeScript 和 Vite，当时讨论过 Tailwind CSS。候选人可粘贴简历和职位描述，或上传 TXT、文本型 PDF，再核对提取结果。后端拟用 FastAPI 在本机解析文件，把文本送给学校端。读取岗位链接也在设想中，网页取不到时仍可直接粘贴 JD。

**面试。** 后端负责保存回答、限制题数与追问次数、处理重复提交，让页面刷新后能接着练。学校 Agent 负责结合本场材料选择问题与追问。每场需要独立标识，怎样传历史当时尚待验证，尤其要避免把同一段上下文在远端和本机重复累积。简历、JD 和网页都只作为资料交给面试官。

**复盘。** 模型根据评分标准找出回答证据，前端展示分项反馈、原文、缺失信息和改进建议，支持导出。历史页用来继续未完面试，也可以围绕薄弱点再练。当时曾讨论让 Agent 查岗位网页或技术资料，并带回真实来源。检索失败时应如实说明，能力评价只用于练习。

拟议目录把页面放在 `frontend/src/`，接口、面试流程、模型连接和报告放在 `backend/app/`，可交付的 Skill 与题库放在 `openclaw/`，测试和文档分别放在 `tests/` 与 `docs/`。持久化拟用 SQLite，曾提议拆成 `interviews`、`messages`、`reports`、`sources` 几张表。远端工作区位置和 Skill 的实际加载情况当时仍需验证。后续实现见[架构与接口约定](architecture.md)。

## 交接时的开发计划

我们计划先搭建项目骨架，补齐配置示例和忽略规则，再用本机凭据完成一次真实模型调用。第一阶段的交付目标是根据一份简历生成一道真实问题，保存一次回答，并得到追问。接下来依次加入持久化、断线恢复、完整复盘、历史记录和导出，最后验证检索工具并准备课程报告、PPT 与演示备份。

当时列出的验收场景包括重复提交、追问上限、刷新和断网恢复，以及简历解析失败、无效模型输出、检索失败和报告引文不符。页面开发可以使用明确标注的模拟数据，学校模型与工具则需要真实调用记录。后续测试结果按日期归入[验证记录](verification.md)。

当时查阅的背景资料包括 [OpenClaw HTTP 接口](https://docs.openclaw.ai/gateway/openai-http-api)、[Skills](https://docs.openclaw.ai/tools/skills) 和 [工具说明](https://docs.openclaw.ai/tools)。学校实例的版本和实际运行结果决定了当天能使用哪些能力。
